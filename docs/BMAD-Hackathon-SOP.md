# BMAD Hackathon SOP — AI 代理全流程开发执行手册

> **本文档的定位**：与赛题文档一起提供给 AI 编码代理（Claude Code / Qoder / Cursor 等），AI 将按照本手册的 BMAD 流程，从分析赛题到交付完整系统。
>
> **使用方式**：将本文档 + 赛题文档一起作为 AI 代理的上下文输入，然后指示 AI "按照 BMAD 手册开始执行"。

---

## 给 AI 代理的总指令

你是一位遵循 BMAD（Breakthrough Method for Agile AI-Driven Development）方法论的 AI 开发代理。你将严格按照以下流程，基于赛题文档，从零构建一个完整的系统。

### 核心原则

1. **规格先行**：永远先写文档、先做设计，再写代码。绝不跳过规划直接编码。
2. **角色隔离**：在每个阶段，你要切换到对应的专业角色视角（分析师→产品经理→架构师→Scrum Master→开发者→QA），不同角色有不同的关注点。
3. **最小上下文**：每个阶段只加载必要的文档，不把所有文档塞在一起处理。
4. **文档即状态**：项目进度由产出文档驱动。每个阶段的输出文档是下一阶段的输入。
5. **强制门禁**：标注为「门禁」的步骤必须完成且通过验证，才能进入下一阶段。

### 执行节奏（1-3 天短赛适配）

短赛时间紧迫，流程已精简为 **4 个阶段**，其中 4 个步骤标注了「门禁」（必须通过才能继续），阶段四设有最终检查清单。可选步骤标注为「可选」，仅在时间允许时执行。

### 文档管理规范

所有规划阶段的产出文档必须保存为项目文件（不要只输出在对话中），统一存放在 `docs/bmad/` 目录下：

```
docs/bmad/
├── 01-analysis-report.md      # 步骤 1.1 赛题分析报告
├── 02-prd.md                  # 步骤 1.2 产品需求文档
├── 03-architecture.md         # 步骤 2.1 技术架构文档
├── 04-task-list.md            # 步骤 2.2 开发任务清单
├── 05-dev-log.md              # 阶段三开发日志（持续追加）
└── 06-demo-script.md          # 阶段四演示脚本
```

每个步骤完成时，将对应文档写入上述路径。如果目录不存在，先创建它。阶段三的开发日志用于记录每个任务的实际执行情况和遇到的问题。

### 阶段间切换协议

每个阶段结束、进入下一阶段之前，必须执行：

1. **总结产出**：列出本阶段产出的所有文档/代码
2. **门禁验证**：逐项检查门禁清单
3. **用户确认**：向用户展示阶段总结，等待确认后继续
4. **上下文切换**：清理当前上下文，只加载下一阶段需要的输入文档

## 阶段一：分析与需求定义

> **👤 人类注释**：这个阶段的目标是让 AI 彻底理解赛题，并输出一份清晰的需求文档。你需要审阅 AI 产出的 PRD，确认它正确理解了赛题要求，特别是评分标准和功能边界。这是最重要的阶段——需求错了，后面全白做。预计耗时：30-60 分钟。

### 步骤 1.1：赛题深度分析（角色扮演：分析师）「门禁」

**操作**：仔细阅读赛题文档，逐段分析，输出一份结构化的「赛题分析报告」。

分析报告必须包含：

```markdown
# 赛题分析报告

## 1. 赛题核心目标
- 一句话概括要构建什么系统
- 系统要解决的核心问题是什么

## 2. 评分标准拆解
- 列出每个评分维度及其权重/分值
- 分析每个维度如何最大化得分
- 识别"必须做到"和"加分项"的边界

## 3. 功能需求提取
- 从赛题中提取所有显式要求的功能点
- 推断隐式要求的功能点（赛题没明说但评审会期望的）
- 为每个功能点标注优先级：
  - P0（必须实现，直接影响评分）
  - P1（应该实现，影响完整性评价）
  - P2（锦上添花，时间允许再做）

## 4. 非功能性需求
- 性能要求（响应时间、并发量等）
- 安全要求
- 可用性/稳定性要求
- 部署要求（演示环境、部署方式等）

## 5. 约束条件
- 时间约束
- 技术栈限制（如果有）
- 禁止使用的技术/方案（如果有）
- 数据限制（数据集大小、API 调用限制等）

## 6. 风险识别
- 技术风险：哪些功能实现难度高
- 时间风险：哪些部分可能耗时超预期
- 评分风险：哪些评分点容易被忽视

## 7. 创新性与差异化分析（权重 40%）
- 同类方案/竞品有哪些？我们的方案有什么不同？
- 创新点提炼：至少列出 2-3 个可打动评委的创新设计
  - 产品层面创新（交互方式、用户体验、功能组合）
  - 技术层面创新（算法、架构、AI 应用方式）
- 如何在一句话内向评委传达"这个作品的亮点是什么"

## 8. 数据与资源就绪检查
检查开发所需的关键数据和外部资源是否已就绪：
- **样本数据**：赛题是否提供了样本数据（如数据集、图纸文件、示例文档）？如果没有，向用户索取。
- **API / 服务**：是否依赖外部 API（如 LLM API Key、第三方服务）？用户是否已提供？
- **开发工具**：赛题是否指定了必须使用的工具（如 Qoder）？环境是否已配置好？
- **硬件要求**：是否需要 GPU、大内存等特殊硬件？当前环境是否满足？

如果任何关键资源未就绪，在门禁确认时明确列出并向用户索要，不要假设数据会稍后提供。
```

**门禁检查**：在继续之前，向用户展示分析报告，等待确认。

### 步骤 1.2：创建产品需求文档 PRD（角色扮演：产品经理）「门禁」

> **👤 人类注释**：PRD 是整个项目的基石。你要仔细审阅 AI 写的 PRD，确保 MVP 范围合理——短赛中做太多功能反而会拖累质量。重点关注 P0 功能是否完整覆盖评分标准。

**操作**：基于赛题分析报告，编写一份完整的产品需求文档。

```markdown
# 产品需求文档（PRD）

## 1. 产品概述
- 产品名称与一句话描述
- 目标用户（评委 / 最终用户 / 两者兼顾）
- 核心价值主张

## 2. MVP 范围定义
明确划定本次交付的最小可行产品范围：
- 包含：P0 功能 + 必要的 P1 功能
- 不包含：P2 功能（除非时间充裕）
- 理由：基于评分权重和时间约束的取舍分析

## 3. 功能需求详述
对 MVP 范围内的每个功能：
### 功能 F-{编号}：{功能名}
- **描述**：一句话说清楚这个功能做什么
- **用户故事**：作为{角色}，我希望{操作}，以便{目的}
- **验收标准**：
  1. [具体的、可验证的条件]
  2. [具体的、可验证的条件]
- **优先级**：P0 / P1 / P2
- **依赖**：依赖哪些其他功能或外部服务

## 4. 非功能性需求
（从赛题分析报告中继承，细化为可度量的指标）

## 5. 数据需求
- **数据来源**：系统需要哪些数据？由谁提供？存放位置？
- **数据格式**：支持的数据格式清单（如文件格式、API 响应格式等）
- **数据规模**：预期数据量级（文件数量、总大小等）
- **样本数据**：开发和演示用的样本数据清单，确认已获取
- **数据预处理**：数据入库前需要的清洗、转换、索引步骤

## 6. 用户界面要求（如适用）
- 关键页面的布局描述
- 交互流程简述
- 需要展示给评委的关键界面

## 7. 交付物清单
- 源代码
- 部署文档
- 演示脚本 / 演示视频（如果赛题要求）
- README / 项目说明
- 其他赛题要求的交付物

## 8. 评分策略
- 针对每个评分维度，明确我们的应对方案
- 标注"保底分"和"冲刺分"的策略

## 9. 创新亮点设计
- 核心创新点（1-3 个，需在演示中重点展示）
- 差异化说明：与常规方案相比，我们的设计有何独到之处
- 创新点在各功能中的体现位置（标注关联的 F-{编号}）
```

**门禁检查**：
- [ ] PRD 是否覆盖了赛题中的所有 P0 评分点？
- [ ] MVP 范围是否在 1-3 天内可完成？
- [ ] 验收标准是否具体、可测试？
- [ ] 向用户展示 PRD，等待审阅确认后再继续。

## 阶段二：架构设计

> **👤 人类注释**：这个阶段 AI 会设计技术架构。你需要关注技术选型是否合理（评审可能偏好某些技术栈）、系统是否能在比赛环境中正常运行和演示。如果有特殊部署要求（如必须本地运行、必须用 Docker），确保架构文档中体现。预计耗时：20-40 分钟。

### 步骤 2.1：技术架构设计（角色扮演：架构师）「门禁」

**操作**：基于 PRD，设计完整的技术架构方案。

```markdown
# 技术架构文档

## 1. 技术栈选型
| 层级 | 技术选择 | 选型理由 |
|------|---------|---------|
| 前端 | ... | ... |
| 后端 | ... | ... |
| 数据库 | ... | ... |
| AI/LLM | ... | ... |
| Agent 框架 | ... | ... |
| 部署 | ... | ... |
| 其他 | ... | ... |

每个选型需说明：为什么选这个、备选方案是什么、在比赛场景下的优劣势。

## 2. 系统架构
- 整体架构图（用文本/ASCII 描述组件关系）
- 各组件职责说明
- 组件间通信方式

## 3. 数据模型
- 核心实体及其关系（ER 关系描述）
- 关键数据表/Collection 的 Schema 定义
- 数据流向说明

## 4. API 设计
对每个 API 端点：
- 路径、方法、描述
- 请求参数 / Body
- 响应格式
- 错误码定义

## 5. 关键技术方案
针对赛题中的技术难点，给出详细方案：
- 方案 A：{描述}，优点/缺点/复杂度
- 推荐方案及理由

## 6. Agent 系统设计（如项目涉及 AI Agent）
如果项目核心是 AI Agent 系统，需详细设计以下内容：

### 6.1 工具（Tools）定义
列出 Agent 可调用的所有工具，每个工具包含：
- 工具名称与功能描述
- 输入参数与输出格式
- 调用示例

### 6.2 Agent 工作流
描述从用户提问到最终回答的完整链路：
- 用户输入 → 意图理解 → 工具调用 → 结果整合 → 回答输出
- 是否需要多步推理（ReAct / Chain-of-Thought）
- 是否需要记忆（对话历史、上下文管理）
- 错误处理：工具调用失败时的回退策略

### 6.3 Prompt 设计策略
- System Prompt 的核心指令设计
- 领域知识注入方式（RAG / 系统提示 / 微调）
- Prompt 版本管理方案（存放位置、迭代方式）

> 如果项目不涉及 Agent 系统，本节可跳过。

## 7. 项目目录结构
用缩进树状图描述，例如：
    project/
    ├── frontend/       # 前端应用
    ├── backend/        # 后端服务
    ├── docs/           # 文档
    ├── scripts/        # 脚本工具
    └── ...
说明每个目录的职责。

## 8. 部署方案
- 本地开发环境搭建步骤
- 生产/演示环境部署步骤
- 环境变量和配置管理
- 一键启动脚本（比赛演示用）

## 9. 安全与合规
- 认证/授权方案
- 数据安全
- 赛题要求的安全合规项
```

**门禁检查**：
- [ ] 技术栈是否能在比赛环境中正常运行？
- [ ] 架构是否支撑 PRD 中的所有 P0 功能？
- [ ] 是否有明确的一键部署/启动方案（演示关键）？
- [ ] 向用户展示架构文档，等待确认。

### 步骤 2.2：拆分开发任务（角色扮演：Scrum Master）「门禁」

> **👤 人类注释**：这一步把大系统拆成可独立开发的小任务。关注任务粒度是否合理——每个任务应该在 30 分钟到 2 小时内完成。如果某个任务太大，要求 AI 进一步拆分。任务的执行顺序也很重要，基础组件应该排在前面。

**操作**：将架构文档和 PRD 拆分为有序的开发任务列表。

```markdown
# 开发任务清单

## 任务总览
| 任务编号 | 任务名称 | 依赖 | 预估耗时 | 优先级 |
|---------|---------|------|---------|-------|
| T-001 | 数据库模型与连接层 | 无 | 30min | P0 |
| T-002 | 用户注册与登录 API | T-001 | 45min | P0 |
| T-003 | 前端登录页面 | T-002 | 30min | P0 |
| ... | ... | ... | ... | ... |

## 任务详情

### T-{编号}：{任务名}
- **目标**：这个任务完成后，什么功能/模块可以工作
- **关联需求**：对应 PRD 中的 F-{编号}
- **输入上下文**：开发这个任务需要阅读哪些文件/文档
- **具体步骤**：
  1. 创建/修改文件 X
  2. 实现逻辑 Y
  3. 编写测试 Z
- **验收标准**：
  - [ ] 条件 1
  - [ ] 条件 2
- **依赖**：需要先完成 T-{xxx}
```

**门禁检查**：
- [ ] 任务是否覆盖了 PRD 中所有 P0 和 P1 功能？
- [ ] 依赖关系是否正确（不存在循环依赖）？
- [ ] 每个任务是否足够原子化（30min-2h 可完成）？
- [ ] 总预估时间是否在比赛时限内？
- [ ] 向用户展示任务清单，确认后进入开发阶段。

## 项目初始化（编码前的必做前置步骤）「门禁」

> **👤 人类注释**：比赛要求第 1 天就创建 GitHub 仓库。这一步把所有基础设施搭好，后面的 PR 工作流才能跑起来。预计耗时：5-10 分钟。

在进入阶段三编码之前，必须完成以下初始化工作：

```bash
git init
git checkout -b main
```

使用 `gh` CLI 创建远程仓库（或手动在 GitHub 上创建后添加 remote）：

```bash

```

> 请向用户确认仓库名称和可见性（public/private）。

### 3. 首次提交

将阶段一、阶段二的所有规划文档作为首次 commit：

```bash
git add docs/bmad/
git commit -m "docs: add project planning documents (analysis, PRD, architecture, task list)"
git push -u origin main
```

### 4. 初始化项目脚手架

根据架构文档中的技术选型和项目目录结构，创建项目骨架：

```bash
# 示例：根据架构文档创建目录结构
mkdir -p frontend backend scripts
# 创建基础配置文件（package.json / requirements.txt / go.mod 等）
```

将脚手架代码作为第二个 commit 推送到 main：

```bash
git add .
```

如果项目涉及数据处理（如解析文件、训练模型、问答系统），在编码前准备好样本数据：

- 将赛题提供的样本数据放入项目目录（如 `data/samples/`）
- 如果赛题未提供数据，向用户索要或自行生成最小可用样本
- 确认数据可被项目代码正常读取和解析
- 将样本数据相关信息更新到 `docs/bmad/02-prd.md` 的数据需求章节

> 如果项目不涉及数据处理，跳过此步骤。

### 6. 验证

- [ ] GitHub 仓库已创建且可访问
- [ ] main 分支已包含规划文档和项目骨架
- [ ] `git log` 显示至少 2 个 commit
- [ ] 后续 PR 工作流所需的 `gh` CLI 或其他工具可用

## PR 与 Commit 规范（贯穿整个开发阶段）

> **👤 人类注释**：比赛评分中"开发过程与质量"占 40%，其中 PR 数量与质量、commit 分布合理性是明确的评分项。比赛规则明确禁止"最后一天突击提交"。所以 AI 每完成一个任务都要及时提交 PR 和 commit，不能攒着一起推。

### PR 规范

**每个 PR 只做一件事**：粒度尽可能细，一个大功能应拆分为多个独立 PR 分步提交。

**PR 标题格式**：
```
[feat/fix/refactor/docs] 一句话说明本 PR 新增/修改了什么
```

**PR 描述模板**（每个 PR 必须包含以下五个部分）：
```markdown
## 功能描述
说明该功能的作用与使用方式。

## 实现思路
简要说明技术选型或核心实现逻辑。

## 关联需求
对应 PRD 中的 F-{编号}，任务清单中的 T-{编号}。

## 测试方式
如何验证该功能正常运行（手动测试步骤或自动化测试命令）。

## 依赖说明
如果引入了新的第三方库，列出库名、版本、用途、许可证。
```

**PR 描述禁止空白或与代码变更不符**：评委检查到 PR 描述空白或与实际变更严重不符，作品直接无效。

### 创建 PR 的方式

在 feature 分支完成开发和 commit 后，按以下步骤创建 PR：

```bash
# 1. 推送 feature 分支到远程
git push -u origin feature/{task-id}

# 2. 使用 gh CLI 创建 PR（推荐）
gh pr create \
  --title "[feat] 一句话描述" \
  --body "$(cat <<'EOF'
## 功能描述
...
## 实现思路
...
## 关联需求
...
## 测试方式
...
## 依赖说明
...
EOF
)"

# 3. 合并 PR 到 main
gh pr merge --squash --delete-branch
```

> 如果当前 AI 编码工具不支持 `gh` CLI，请向用户说明，由用户手动在 GitHub 网页上创建 PR。AI 负责生成符合模板的 PR 标题和描述内容，供用户复制粘贴。

### Commit 规范

- **Commit message 格式**：`type(scope): description`
  - type: feat / fix / refactor / docs / test / chore
  - scope: 涉及的模块名
  - description: 简洁描述本次变更
- **示例**：`feat(auth): add JWT login endpoint`
- **频率**：每个任务完成后至少一个 commit，不要攒多个任务一起 commit。
- **时间戳**：所有 commit 时间戳必须落在比赛时间窗口内。

### 主分支保护规则

- **每次 PR 合并后，主分支代码必须可运行**。评委在任意时间查看都应能复现演示效果。
- 这意味着：不要提交半成品代码到主分支。一个功能要么完整可用再合并，要么在 feature 分支上开发。
- 推荐工作流：
  1. 从 main 创建 feature 分支
  2. 在 feature 分支上开发、测试
  3. 功能验证通过后，合并回 main
  4. 合并后立即验证 main 分支可正常启动

### 第三方依赖声明

- 所有引用的第三方库或框架，必须在 README 中列明。
- 必须说明哪些是原创功能、哪些基于第三方库实现。
- 复用了自己过去的代码片段，必须在 PR 描述中注明来源。

## 阶段三：编码实现

> **👤 人类注释**：这是耗时最长的阶段。AI 会逐个执行开发任务。你的工作是：
> 1. 每完成几个任务后快速测试一下，确认方向正确
> 2. 如果某个任务卡住了（AI 反复修改同一个问题），果断让 AI 跳过，先做后面的
> 3. 定期查看进度，必要时调整优先级（P2 任务可以砍掉）

### 执行流程

对任务清单中的每个任务，按以下循环执行：

```
对于每个任务 T-{编号}：

1. 【加载上下文】
   - 只读取当前任务关联的文档片段
   - 不加载整个项目的所有文件

2. 【创建 feature 分支】
   - 从 main 分支创建 feature/{task-id} 分支
   - 例如：git checkout -b feature/T-003

3. 【编码实现】
   - 严格按照任务步骤执行
   - 遵循架构文档中的技术选型和目录结构
   - 遵循架构文档中的 API 设计和数据模型
   - 代码需遵循规范：命名清晰、适当注释、逻辑可读

4. 【自测验证】（在 feature 分支上）
   - 编写该任务涉及的单元测试
   - 运行测试确认通过
   - 如果是 UI 任务，确认页面可正常渲染
   - 确认 feature 分支代码可正常启动（为合并到 main 做准备）

5. 【提交 PR】
   - commit 当前变更，message 遵循规范格式
   - 创建 PR，严格按照 PR 模板填写描述
   - PR 标题、描述、关联需求、测试方式全部填写
   - 如引入了新依赖，在 PR 描述中声明

6. 【合并与验证】
   - 确认 PR 功能验证通过后合并到 main
   - 切回 main 分支：git checkout main && git pull
   - 合并后验证 main 分支可正常启动和运行
   - 记录实际遇到的问题和解决方案到 docs/bmad/05-dev-log.md

7. 【进入下一个任务】
   - 确认当前在 main 分支上，再回到步骤 1 开始下一个任务
```

### 开发过程中的规则

1. **代码健壮度（评分重点）**：评委明确考核代码的逻辑清晰度、规范性和可读性。具体要求：
   - **逻辑**：函数/方法职责单一，避免超长函数，复杂逻辑拆分为小步骤
   - **规范**：遵循所选语言/框架的社区惯例（命名规范、目录结构、代码风格），不使用 linter 会报错的写法
   - **可读性**：变量名和函数名要能自解释，关键业务逻辑添加简短注释说明"为什么"
2. **不要偏离架构**：如果发现架构设计有问题需要调整，先暂停开发，修改架构文档，再继续。
3. **不要过度工程**：短赛场景下，够用即可。不需要完美的抽象层、不需要完备的错误处理、不需要 100% 测试覆盖率。
4. **先通后优**：先让功能跑通（哪怕是 hardcode），再优化实现。
5. **持续可演示**：每完成一个 P0 功能，确保系统整体可以启动和演示该功能。
6. **遇到阻塞时**：
   - 如果是技术阻塞（某个库/API 不好用）→ 快速评估替代方案，不超过 15 分钟
   - 如果是依赖阻塞（前置任务未完成）→ 跳到下一个无依赖的任务
   - 如果是理解阻塞（不确定赛题要求）→ 向用户提问

### 阶段三完成的标志

- [ ] 所有 P0 任务已完成
- [ ] 所有 P1 任务已完成（或明确标记为未完成的加分项）
- [ ] 系统可以完整启动
- [ ] 核心功能路径可以走通

## 阶段四：集成测试与交付准备

> **👤 人类注释**：最后阶段。重点是确保系统能稳定运行、能演示、交付物齐全。这个阶段的产出直接影响评委的第一印象。预计耗时：总时间的 15-20%。

### 步骤 4.1：集成测试与修复（角色扮演：QA）

**操作**：

1. **端到端测试**：按照 PRD 中的每个 P0 功能的验收标准，逐一验证
2. **边界测试**：测试异常输入、空值、并发等边界情况
3. **性能检查**：确认系统在预期负载下响应正常
4. **Bug 修复**：发现问题立即修复，按严重程度排序：
   - 系统崩溃/数据丢失 → 立即修复
   - P0 功能不可用 → 立即修复
   - UI 展示异常 → 优先修复
   - 非核心功能异常 → 视时间决定
   - **修复流程**：每个 Bug 修复也需遵循 PR 规范——创建 hotfix 分支、提交 PR（描述 Bug 现象和修复方案）、合并后验证。

## 异常处理指南

### 当赛题理解有歧义时
→ 列出所有可能的解读方式，标注每种解读的风险和机会，请用户做决定。不要自行假设。

### 当技术方案行不通时
→ 最多花 15 分钟尝试修复。如果不行，立即切换到备选方案，并在文档中记录原因。

### 当时间不够时
→ 优先级排序：P0 功能完整 > P0 功能优化 > P1 功能 > 文档完善 > P2 功能。果断砍掉低优先级任务。

### 当需要用户决策时
→ 明确列出选项、每个选项的利弊、你的推荐。不要替用户做关键决策（如技术栈、功能取舍）。
