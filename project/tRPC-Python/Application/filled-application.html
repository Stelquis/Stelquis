📌 一、背景与动机

tRPC-Agent-Python 当前提供了一套完整的 Agent 构建、编排、工具接入、会话记忆等能力，但在生产级部署上仍处于"单机可跑"的阶段。当需要将同一个 Agent 服务同时开放给多个业务方时，就暴露出几个现实问题：

  • 不同租户的模型配置（一个用 DeepSeek、一个用 GPT-4）如何隔离？
  • 每个租户的会话数据、知识库、审计日志是混在一起还是分开存？
  • 如果 Agent 流量大了，能否横向加机器而不中断现有会话？

这些问题的本质是 多租户隔离 + 节点水平扩展 两个架构维度的缺失。我选择这个课题，是因为它恰好位于"框架功能完备"和"生产可用"之间的过渡地带——解决了它，Agent 框架才能真正从示例走向企业级服务。

🔧 二、技术方案

2.1 核心模块设计

整个方案围绕 四个核心模块 展开，每个模块解决一个独立的架构问题：

🏗️ 模块一：租户模型与配置隔离

设计 Tenant 数据模型，核心字段包括：tenant_id（唯一标识）、model_config（模型提供商、API Key 引用、模型名称）、tool_whitelist（允许使用的工具列表）、channel_binding（IM 通道配置）、audit_policy（审计等级与日志保留策略）。每个租户独立存储配置，运行时不交叉读取。

⚡ 难点：API Key 不能明文存储，但又要能在运行时被 Worker 读取。方案是在 Tenant 表中只存 Key 的引用 ID，实际密钥由密钥管理服务持有，Worker 按需获取。

🌐 模块二：节点部署拓扑与无状态 Worker

设计四类节点：Agent Gateway（统一入口，按 tenant_id + session_id 路由请求）、Agent Worker（无状态，只负责执行 Agent 逻辑，不持有任何会话数据）、Storage Adapter（统一数据访问层）、Telemetry Collector（全链路追踪）。关键决策是：不依赖 Sticky Session——所有会话状态存入共享 Redis/SQL 后端，Worker 自由扩缩容。

🔑 突破口：tRPC-Agent 的 SessionService 抽象层本就是多后端可切换的，已有 InMemory、SQL、Redis 三种实现。Storage Adapter 只需要在此基础上包一层租户路由逻辑。

🗄️ 模块三：统一数据访问抽象

设计 StorageRouter，根据 tenant_id 查找该租户的后端配置，将请求路由到正确的存储实例。覆盖的数据类型：Session Memory Summary Knowledge AuditLog。

⚡ 难点：不同后端的写入一致性模型不同——Redis 是最终一致，SQL 是强一致。需明确每个数据类型的一致性取舍。

💬 模块四：IM Channel Adapter

设计 Adapter 接口，将外部 IM 消息统一转换为 tRPC-Agent 的 NewMessage 输入。计划覆盖企业微信（WeCom）和 Telegram 两类通道，重点处理消息验签、消息去重、用户身份映射、群聊/单聊的 session_id 生成规则。
