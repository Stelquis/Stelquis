## 1.1 项目背景

Easy-Es 是国内 Top1 的 Elasticsearch ORM 框架（Gitee 5.8K star / 1.8K fork，GVP 项目），把 ES 的高门槛封装成 MyBatis-Plus 风格的 API。项目由 Dromara 社区孵化，作者为「老汉」（`xpc1024`）。

维护目前高度集中于作者一人（核实数据见 §2.1）。项目需要的不是单点功能补充，而是一套能把「需求发现 → 设计 → 实现 → 验证 → 提交」串起来的自动化设施，使维护者从逐条处理 Issue 转为审核 AI 产出。

## 1.2 基本需求

| # | 产出要求 | 优先级 | 实施要点 |

| 1 | 基于 Skills 的爬虫，抓 GitHub/Gitee Issue 及 ES 官方动态 | P0 | 技术成熟，难点在数据质量而非抓取本身 |
| 2 | AI 自动选题与进化方向挖掘，支持人工审核与自主指定 | P0 | 全链路中最依赖领域判断的一环 |

- 产出 5 的「基于真实需求」排除了构造演示需求走通流水线的做法。对应验收要求：**每个 AI 生成的 PR，需求可溯源到具体 Issue 编号或 ES 官方动态条目**。
- 产出 2 的「进化方向挖掘」若由 LLM 自由发挥，会产出「建议增强可观测性」这类无法证伪也无法落地的建议。该环节产出将**强制结构化**：不是自由文本，而是带证据链的候选列表。

# 二、项目理解

## 2.1 痛点核实

任务书描述的「可能放缓」已经发生。

## 2.2 关键判断

**判断一：项目属于元工程，验收是非线性的。**

交付物不是单个功能，而是能产出功能的系统。即便 90% 的模块正常运行，只要产出的 PR 是垃圾，整体价值就归零。因此验收以**产出质量**而非功能完成度为准。

**判断二：脏活占比约 80%。**

| 工作项 | 占比 |
|---|---|
| 建验证闭环（编译 / 测试 / 分层反馈） | 25% |
| 搭环境（ES 容器 / 依赖冲突 / JDK 矩阵） | 25% |
| 爬 Issue + 数据清洗 + 分类器标注 | 15% |
| 建能力图谱（读码 / 切分 / 验证 RAG 命中） | 15% |
| 调 LLM / Prompt / RAG | 15% |
| 架构与设计创新 | 5% |

环境与验证合计占 65%。这一分布决定了排期：前两个月先做环境与验证，而非先搭 Agent 框架。

**判断三：难度集中在三处。**

1. LLM 能否生成通过 Easy-Es 全套测试的 Java 代码，取决于验证反馈设计
2. 能否筛出「值得做且 AI 能做对」的需求，取决于领域判断
3. RISC-V64 的验收口径，需与导师确认（§10.4 Q1）

# 三、前期调研

> 数据获取时间：2026 年 9 月 4 日。

## 3.1 代码库体量与改动链路

**体量**（v3.0.2 标签实测）：Java 主源码 198 个文件、24,647 行；测试 49 个文件、7,254 行。`easy-es-core` 独占 17,696 行（71.8%），是能力图谱与代码生成的主体。条件构造器对外暴露 898 个方法（`Compare` 321 / `Func` 304 / `Geo` 150，其余 123）；`FieldType` 枚举 27 个值，注解 14 个。

**改动链路**：新增一个查询 API 需横跨 5 个文件层级——

| 层 | 文件 | 职责 | 行数 |
|---|---|---|---|
| ① | `conditions/function/Func.java`（或 `Compare.java`） | 接口声明 + javadoc | 1790 / 2215 |
| ② | `kernel/AbstractWrapper.java` | 实现 + 参数校验 | 1027 |
| ③ | `kernel/AbstractChainWrapper.java` | Lambda / 链式重载 | 791 |
| ④ | `kernel/WrapperProcessor.java` | ES DSL 序列化 | 1101 |
| ⑤ | `toolkit/FieldUtils.java` | `.keyword` 后缀判定 | 292 |

漏任何一处都会导致**能编译但语义错误**：编译器不会报错，只有测试能发现，而测试失败信息未必能反推出根因。

`LambdaEsQueryWrapper` 全文仅 53 行、4 个方法（2 个公有构造器、1 个包内构造器、1 个 `instance()` 覆写），不含任何查询方法；其父类 `AbstractLambdaQueryWrapper` 是 13 行空壳，实现在 `AbstractWrapper`。按「在 `LambdaEsQueryWrapper` 里加方法」的直觉去改，会直接改错文件。

改动高度集中：`Compare` + `Func` + `AbstractWrapper` + `WrapperProcessor` 共 6,133 行（占主源码 25%），是几乎每个 API 改动都要触碰的窄口，L1 定向单测优先覆盖这四个文件。

**其余领域约束：**

- **`.keyword` 智能后缀**：按字段索引类型 + 查询类型上下文判定，逻辑在 `FieldUtils.java:210-237`，可用 `smartAddKeywordSuffix=false` 关闭。v3.0.0 release note 中「修复聚合 / 排序 / prefix 查询时部分字段未加 .keyword 后缀」佐证其易错性。
- **id 列约定**：v3.0.0 起支持自定义名称，不再强制 `id`，但默认约定仍为 `id`。2.x 文档中「实体类必须含 `String id`」已过时。
- **依赖版本**：底层为 `elasticsearch-java`，锁死 7.17.28，涉及 `elasticsearch-java` / `elasticsearch` / `elasticsearch-geo` 三个构件；Spring Boot 内置 starter 需排除后显式声明。ES 服务端 7.x / 8.x 均可，JDK 兼容 8 / 17 / 22。
- **覆盖率基线**：官方宣称单元测试综合覆盖率超 95%。这既提供了 L1 定向单测的高质量语料库，也意味着新增 PR 不附带测试即不符合社区标准。

**版本节奏**：v3.0.0（2025-05-11）为架构级重构（换 `elasticsearch-java` 7.17.28、弃 fastjson 换 jackson），2.x 资料已过时；v3.0.1（2026-02-27）引入向量检索 beta；v3.0.2（2026-05-10）仅 1 条 fix。

## 3.2 Issue 生态实测

对 GitHub 最新 30 条 open issue（#135–#171，2024-09 至 2026-08）人工分类：

| 类型 | 数量 | 占比 | 示例 |
|---|---|---|---|
| **feature request** | 8 | 约 27% | #169 suggest 自动补全、#168 nginx pathPrefix、#156 flattened 类型、#154 `@IndexField(index=true)`、#147 动态数据源、#146 时区与缺失的 `ge` 方法 |
| **bug** | 9 | 约 30% | #167 管道聚合从第 3 个字段起丢失、#164 `_score` 排序被强制排到末尾、#170 map 字段序列化 |
| 求助 / 噪音 | 13 | 约 43% | #171 外部安全问卷、#166「支持 SpringBoot4 吗」、#159 https 如何配置、#141 IDEA 报红 |

实测分布与依据《避坑指南》作者自述所作的估计（可转化需求低于 10%）差异较大。据此确定两点：候选池充足（feature 加 bug 合计约 57%），R2 风险下调至低；噪声仍占 43%，分类器保留。相应地，W4 先人工标注 200–300 条样本再训练分类器，而非依赖先验推测。

## 3.3 三处待澄清的不一致

**一、底层客户端表述在 5 处公开材料中各不相同。** Gitee README 正文已更新为 ElasticsearchClient，仓库简介、GitHub README、Gitee 项目标签、官网「特性」区仍为 RestHighLevelClient。若爬虫语料混入仍在流通的 2.x 文档，检索结果会自相矛盾，故能力图谱以 3.x 源码为唯一事实来源。

**二、Issue 状态与代码实际能力脱节。** #143「需要 es8.0 以上支持」已由 v3.0.0 完成；#135「能否支持 es8.x 的向量搜索」已由 v3.0.1 引入 beta；#157「createIndex() 无法重复使用」已由 v3.0.1 修复。三者至今仍为 open。这说明「某功能是否已实现」即使对 Maintainer 也不易判定，是能力图谱闭环的直接依据。

**三、RISC-V64 验收口径。** 任务书标注「支持架构：RISC-V64」，官方 README 宣称「兼容 jdk8 至 jdk17 支持 RISC-V 架构」（同一行又写「兼容 jdk8~jdk22」），而 Elastic 官方支持矩阵无 riscv64 构建。处理方案见 §10.4 Q1。

## 4.1 能力天花板：学术基准数据

SWE-bench Multilingual（300 任务 / 42 仓库 / 9 语言），SWE-agent + Claude 3.7 Sonnet、单任务成本上限 $2.50：

| 语言 | 解决率 | 语言 | 解决率 |
|---|---|---|---|
| Rust | 58.14% | JavaScript / TypeScript | 34.88% |
| **Java** | **53.49%** | Go | 30.95% |
| PHP | 48.84% | C / C++ | 28.57% |
| Ruby | 43.18% | 整体 | 42.67% |
| 参照：SWE-bench Verified（Python） | 63% | | |

**落差**：Java 与 Python 相差约 10 个百分点，幅度小于常见预估。

**基准偏乐观**：gold patch 中位仅 10 行、95 分位 110 行（论文明确列出的局限）。Easy-Es 新增一个查询 API 需横跨 5 个文件层级，故 53.49% 是乐观上界。

**瓶颈归属**：论文对成功 / 失败轨迹的人工检查发现行动分布高度相似，说明瓶颈在模型能力而非 Agent 设计。据此，工程投入放在验证反馈密度而非编排复杂度。

同基准中 `apache/lucene`（Java）解决率仅 33.3%——Lucene 是 Elasticsearch 的底层库，与本项目领域直接相关。

## 6.2 主要难点

# 八、技术方案

## 8.1 设计原则

| # | 原则 | 含义 |
|---|---|---|
| P1 | 客观信号优先 | 质量判定优先采信编译、测试、覆盖率、静态扫描等硬信号；LLM 评审不作放行依据 |
| P2 | human-in-the-loop 而非 human-on-the-loop | 人工介入是流程节点（选题、设计、PR 提交前），不是异常时的补救 |
| P3 | 反馈密度优先于编排复杂度 | 依据 §4.1 瓶颈归属结论，工程投入放在「让模型更快知道自己错了」 |
| P4 | 可降级、可熔断 | 任何环节失败都能安全停在当前状态 |
| P5 | 不追求通用 | 只针对 Easy-Es 单仓库做深 |

## 8.2 系统架构

七个模块由统一状态机（Python）编排，每步产出落盘为结构化 JSON / Markdown，验证失败沿虚线反馈重试：

| 模块 | 职责 |
|---|---|
| M1 感知层 | Gitee / GitHub Issue + ES 官方动态抓取 |
| M2 选题层 | 能力图谱 RAG + 是否已实现校验 + 评分排序（全链路最依赖领域判断的一环） |
| M3 设计层 | 架构 / 详细设计生成 + 自动 Review |
| M4 生成层 | Java 代码 + 单元测试生成 |
| M5 验证层 | L0 / L1 / L2 分层验证 + 客观信号采集（技术内核） |
| M6 交付层 | 分支 / Commit / PR 描述生成 |
| M7 管控层 | Token / 超时 / 重复输出熔断 / 全链路审计（横切约束 M1–M6） |

编排采用**显式状态机**而非 Agent 自主决策：状态迁移条件、重试上限、失败分支全部显式编码，可预测、可回放、易熔断。三处强制人工门禁：选题确认 → 设计确认 → PR 提交前确认。

## 8.3 实现单元分解

| # | 实现单元 | 输入 | 产出 | 通过标准 |
|---|---|---|---|---|
| U1 | Issue 抓取器 | Gitee/GitHub API、ES Release Notes | SQLite 候选池 | 增量同步无遗漏，字段完整 |
| U2 | 四分类器 | 候选池原始条目 | `feature_request`/`bug`/`question`/`noise` | 准确率 ≥ 85% |
| U3 | 能力图谱构建器 | 3.x 源码（`core`/`annotation`/`common`） | 两级切分索引 + BGE/BM25 混合检索 | 30–50 条测试集命中率 ≥ 80% |
| U4 | 选题评分器 | 候选 + 检索结果 | 八字段结构化条目（含 `source_issue`） | 需求 100% 可溯源 |
| U5 | 设计生成器 | 选定需求 + 相关代码上下文 | `architecture.md` / `detailed_design.md` | 改动清单完整 |
| U6 | 一致性校验器 | 设计声明 vs 实际 diff | 校验报告 | 能检出漏改的链路层级 |
| U7 | 代码生成器 | 设计文档 + 硬约束 | 基于 diff 的定向改动 | 改动面不超出设计声明 |
| U8 | 单测生成器 | 新增代码 | 对应测试用例 | 覆盖率不低于现有 95% 基线 |
| U9 | L0 验证器 | 编译产物 | 编译 + checkstyle/spotbugs + 依赖校验 | 耗时 < 30s，拦截率 ≥ 60% |
| U10 | L1 验证器 | 受影响模块 | 定向单测结果 | 耗时 < 2min，再拦截 ≥ 25% |
| U11 | L2 验证器 | 全仓 | Testcontainers 起真实 ES 的回归结果 | 覆盖三条测试线 |
| U12 | PR 组装器 | 通过验证的 diff | 分支 / Commit / PR 描述（关联 Issue） | 符合社区 PR 模板 |
| U13 | 管控器 | 全流程 | Token / 超时 / 熔断 / 审计 | 重复输出可在 N 轮内熔断 |

## 8.4 方案选型

| 方案 | 优点 | 缺点 | 选择 |
|---|---|---|---|
| A：Agent 自主决策 | 灵活，可处理未预期情况 | 行为不可预测，易失控（§4.3） | 否 |
| B：显式状态机 | 可预测、可回放、易熔断、易调试 | 灵活性受限，需预定义路径 | **选 B** |
| C：整文件重写 | 实现简单 | 易引入无关变更，diff 噪声大 | 否 |
| D：基于 diff 定向修改 | 改动面可控、diff 可审计 | 需准确定位插入点 | **选 D** |
| E：纯向量检索 | 语义匹配好 | 对 Java 标识符等强关键词召回率低 | 否 |
| F：BM25 + 向量混合 | 符号与语义兼顾 | 实现稍复杂 | **选 F** |

选 D 并用 AST 定位辅助插入点确定（借鉴 AutoCodeRover 思路）。

## 8.5 语言与工具选型

Easy-Es 是 100% Java 仓库，但任务书「编程语言」一栏同时列出 JavaPython，且产出要求第一条为「开发基于 Skills 的爬虫模块」。本项目编排层用 Python、产出代码用 Java，两层各司其职。

三条佐证：任务书「编程语言」同列 JavaPython；措辞差异明显（「了解 **Python 编程**」对「了解 **Java 基础**」）；技术要求要求「熟悉 **AI 工程化语言特性**」，该生态事实标准语言为 Python。

Java 侧难度不因主体用 Python 而降低——5 层改动链路与 `.keyword` 约定全部落在 Java 侧，是主要技术风险（N1/N2），W1–W2 集中补强。

**工具链**：Python 3.12 + 显式状态机；可插拔 LLM 适配层（默认 DeepSeek / Qwen，模型版本可锁定）；BGE 嵌入 + 本地向量库 + BM25 混合；Gitee OpenAPI / GitHub REST API；Maven + JDK 8/17/22 + Testcontainers；SQLite + 文件系统；Docker Compose 一键启动。

## 8.6 vibe coding 的工程化约束

任务书技术要求第一条列出「熟练掌握 vibe coding」。vibe coding 指不逐行审查 AI 产出的代码，而是描述意图、运行观察、依据结果迭代，将正确性判断从读代码转移到看行为。

这一模式的前提是**行为反馈足够快且可信**，而 Easy-Es 恰是该前提最脆弱的场景：改动链路漏任何一层的结果是能编译但语义错误；全量测试需 Testcontainers 起真实 ES 耗时 5–15 分钟，若每次迭代都等 15 分钟，日迭代次数被压到十几次。典型失败形态是「跑通了」但结果不对。

本项目不把 vibe coding 当作工具使用，而作为需被工程化约束的对象：

| vibe coding 的缺陷 | 技术响应 |
|---|---|
| 反馈慢，迭代次数被压缩 | M5 分层验证：L0 <30s 拦截 ≥60%，L1 <2min 再拦 ≥25% |
| 反馈不可信，「跑通」误判为「对了」 | P1 客观信号优先，LLM 自评不作放行依据 |
| 无终止条件，易陷循环 | M7 重复输出相似度检测即熔断，重试上限 15 次 |
| 责任边界模糊 | P2 三处强制人工门禁，每步产出落盘可回溯 |

本项目的实质是为 vibe coding 补上其在 Java 生产仓库中缺失的一环——可信、快速、分层的验证反馈。模型能力给定时，vibe coding 的产出质量上限由验证反馈质量决定。

# 九、实施计划

## 9.1 仓库归属与结项合规

| 成果 | 归属仓库 | 合规依据 |
|---|---|---|
| AI 生成的功能模块 PR（结项核心依据） | `gitee.com/dromara/easy-es`（项目详情页指定） | 满足结项标准「以 PR/MR 形式提交到项目所在的开源组织仓库中并完成合并」 |
| Harness 系统代码（过程产物，计入代码贡献量） | 优先争取 `gitee.com/dromara/easy-es-harness`；退而求其次放个人仓库 | 退至个人仓不影响结项资格，仅影响代码贡献量评分 |

Harness 不并入 easy-es 主仓：该项目为 Apache-2.0 纯 Java 项目，混入数千行 Python 编排代码会污染主仓结构并干扰既有 CI。

## 9.2 与上游仓库的边界

源码、Issue、构建与测试信号均为只读；代码改动只在独立工作副本的 feature 分支上进行，不直接写主仓；PR 提交前经人工门禁。**PR 评论写入为最高危操作**，默认关闭自动评论，仅在人工确认后单次执行，全局频次上限为每日不超过 3 次。

## 9.3 系统形态

以 Skills 规范封装四个技能单元（`issue-crawler` / `capability-index` / `design-draft` / `pr-composer`），同时提供纯 CLI 入口，不依赖特定 Agent 运行时亦可独立运行；通过 Docker Compose 一键启动，便于复现与验证。

# 十三、范围边界与可行性结论

## 13.1 基础阶段明确不包含的内容

为避免范围蔓延，以下内容明确不在基础实现目标内：

| 不包含 | 原因 |
|---|---|
| 通用化框架 | P5 原则，仅针对 Easy-Es 单仓库；不做「以后也能用于其他项目」的抽象 |
| 索引托管与数据迁移路径的改动 | 属高风险敏感路径，设为禁区（Q2） |
| 移除人工门禁 / 转向全自治 | §4.1 与 §8.6 表明当前能力天花板不支持 |
| Web UI | 以 CLI + 结构化产物为主，降低范围与维护成本 |
| 多模型自动路由与成本优化 | 与本项目目标无关，属过度工程 |
| 依赖升级类改动（如 Issue #171） | 涉及依赖版本，需导师明确认可后才纳入 |

## 13.2 可行性结论

技术路径可行。能力天花板已量化（§4.1），据此采用 human-in-the-loop 半自动而非全自治；核心矛盾有解（§8.3），分层验证把错误发现成本从 15 分钟压到 30 秒，使 6–35 次迭代在 40 分钟内完成；主要难点逐条有对策（§6.2），已有基础可直接复用（§6.1）。

主要不确定性为导师侧的三项确认（Q1 架构口径、Q2 PR 判定标准、Q3 基线），均已在 §10.4 提出，不影响主体方案，可在 W1 内收敛。
